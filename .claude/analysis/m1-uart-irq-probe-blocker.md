## 1. 结论

M1-T1.3 当前不是被未知的页表、PMP 或 PLIC 故障阻塞，而是被 `examples/uart_irq` 测试夹具自身的三处问题阻塞：

1. probe 在 IRQ 注册前主动向 `UART_BASE + 8` 写入诊断值。QEMU virt 的 ns16550a 只暴露 8 个字节寄存器，合法字节偏移是 `0..=7`；该写入越过设备窗口，StoreFault 与 PLIC 无关。
2. probe 把 `UART_STRIDE` 配成 `4`。`uart_16550 0.5.0` 将逻辑寄存器号乘以 stride；在 QEMU virt 上应使用 stride `1`。若后续调用 `init()`，逻辑 FCR(2) 会落到物理偏移 8，并再次触发同类 fault。
3. probe 只调用 `Uart16550::new_mmio()`，没有调用 `init(Config::default())`，因此 UART `IER.DATA_READY` 没有开启。即使删除越界写，当前程序仍不能生成有效的 UART RX 中断 RED 见证。

此外，当前 IRQ handler 只增加计数，不读取 IIR/LSR/RBR 清除 UART 的 level-triggered RX 条件。PLIC 完成后，这会使 GREEN 测试存在 IRQ storm 风险。

因此推荐解阻动作不是继续调查 PMP，而是先修复 probe，使 RED 见证满足“地址正确、设备确实产生 IRQ、handler 可消除中断源”三个前提，再进入 PLIC T2.1。

## 2. 证据链

### 2.1 StoreFault 发生在 PLIC 路径之前

`run_riscv()` 的执行顺序是：

```text
new_mmio(stride=4)
  -> 页表/PLIC/UART 越界诊断写
  -> write_volatile(UART_BASE + 8)   # StoreFault
  -> register(IRQ 10)                # 尚未执行
  -> set_enable(IRQ 10, true)        # 尚未执行
```

故障点位于 `examples/uart_irq/src/main.rs:211`，IRQ 10 尚未注册，PLIC source 也尚未 enable。该 StoreFault 不能作为 PLIC RED 证据。

### 2.2 stride 的语义与平台配置不匹配

`uart_16550 0.5.0` 的 MMIO backend 使用：

```text
effective_address = base_address + logical_register_offset * stride
```

probe 当前配置 `stride=4`，因此寄存器地址变为：

| 逻辑寄存器 | 索引 | stride=4 | QEMU virt 正确地址 |
|------------|------|----------|--------------------|
| THR/RBR | 0 | `base + 0` | `base + 0` |
| IER | 1 | `base + 4` | `base + 1` |
| FCR/IIR | 2 | `base + 8` | `base + 2` |
| LSR | 5 | `base + 20` | `base + 5` |
| SPR | 7 | `base + 28` | `base + 7` |

本机 QEMU 生成的 DTB 将设备标识为 `ns16550a`、节点为 `uart@10000000`，且 DTB 中不存在 `reg-shift` 属性；这与连续字节寄存器、stride `1` 一致。

### 2.3 `new_mmio()` 不会初始化 UART

`Uart16550::new_mmio()` 只校验 base/stride 并构造 backend。实际设备配置由 `init(Config)` 完成，包括：

- SPR presence test；
- 禁用旧中断并设置 divisor/LCR/FCR/MCR；
- 设置 `MCR.OUT_2_INT_ENABLE`；
- 按 `Config.interrupts` 写 IER。

`Config::default()` 默认包含 `IER::DATA_READY`。当前 probe 导入了 `Config`，但未调用 `init()`，所以没有建立 UART RX IRQ 的硬件前提。

### 2.4 当前 handler 不满足 level IRQ 完成条件

当前 `irq10_handler()` 仅执行原子计数。PLIC complete 只完成控制器侧 claim，不会清除 UART 侧中断原因。RX 数据未从 RBR 取走时，UART 会继续保持 IRQ 10，可能在 GREEN 阶段形成重复进入。

M1 probe 应在 handler 中读取 IIR 确认原因，并在 LSR.DATA_READY 时 drain RBR；至少维护 `irq_count` 与 `rx_byte_count` 两个计数，才能区分“控制器分派次数”和“实际消费字节数”。

## 3. 推荐解阻方案

### 3.1 必做修改

对 `examples/uart_irq` 做最小修正：

1. 将 `UART_STRIDE` 从 `4` 改为 `1`。
2. 删除页表遍历、随机 PLIC 写、`UART + 0x1000` 和 `UART + 8` 写；这些诊断已经完成使命，且越界 MMIO 不应留在测试路径。
3. 先建立 handler 可访问的 UART MMIO 状态，再注册 IRQ 10。
4. 注册成功后调用 `uart.init(Config::default())`，确保 UART 产生 DATA_READY IRQ。由于当前 platform 的 `register()` 内部会调用未实现的 `set_enable()`，RED 阶段仍应出现 PLIC warning 且 handler 计数保持 0。
5. handler 读取 IIR/LSR 并 drain RBR，清除设备侧 level condition；主循环只报告计数，不再与 handler 竞争轮询 RBR。

推荐顺序：

```text
map UART(base=0x1000_0000, stride=1)
  -> publish handler MMIO state
  -> register IRQ 10              # RED: platform set_enable 仍是 TODO
  -> uart.init(Config::default())  # 开启 UART DATA_READY
  -> inject host byte
  -> assert irq_count == 0         # 有效 RED
```

PLIC 完成后的 GREEN 使用同一 probe：

```text
host byte -> UART DATA_READY -> PLIC claim 10
  -> handler: identify + drain RBR + count
  -> PLIC complete 10
  -> assert irq_count/rx_byte_count 增加且无 storm
```

### 3.2 不推荐方案

| 方案 | 判断 | 原因 |
|------|------|------|
| 继续深挖 page table/PMP | 不推荐 | 已确认 fault 发生在显式设备越界写；页表可写不能使设备越界地址合法 |
| 只删除 `+8` 写 | 不完整 | stride 仍错误，调用 `init()` 后会再次越界；UART 仍未开启 RX IRQ |
| 手写 IER/THR/LSR 绕开驱动 | 不推荐 | 会掩盖 stride 和初始化契约，且不足以验证完整 16550 中断源清除 |
| handler 只计数 | 不推荐 | level-triggered RX 条件不清除，GREEN 阶段可能形成 IRQ storm |

## 4. RED/GREEN 验收标准

### 4.1 修复后的 RED

- probe 启动无 StoreFault；
- `register(10)=true`；
- 日志保留 `set_enable is not implemented for IRQ 10`；
- host 注入 1B/64B 后 `irq_count=0`、`rx_byte_count=0`；
- SBI console 持续可用，无 panic、无 unhandled IRQ storm；
- 保存命令、输入方式和完整日志后，T1.3 可标记完成。

### 4.2 PLIC 完成后的 GREEN

- host 注入后 claim 的 IRQ 恒为 10；
- 1B/64B 输入对应 RX 字节计数，无丢失、无无限重复计数；
- disable 区间计数不变，re-enable 后恢复；
- unregister 后不再调用旧 handler；
- 无输入超时场景无 spurious loop；
- SBI console 在 PLIC 初始化前后保持可用。

## 5. 对 OpenSpec 计划的影响

M1 的架构方向、vendor 载体、PLIC context 算法和 T2.1-T4.5 不需要改变。只需修正 T1.3 的测试夹具和验收描述：RED 的必要条件应明确包含正确 stride、UART RX IRQ 已开启、设备中断源可清除。

T1.1 与 T1.2 已由 commit `cfb8d24` 完成；OpenSpec task checkbox 应同步为 2/15。T1.3 在 probe 修复并保存有效 RED 日志前仍保持阻塞。

| 缺陷 | 落地位置 | 修复 |

| handler 未清源 | 重写 `irq10_handler`：read IIR → loop `read(LSR) & drain(RBR)` → `RX_BYTE_COUNT.fetch_add(drained)` | level-triggered RX 条件被清除 |

**最终顺序**（比 §3.1 推荐更稳）：
```
new_mmio(stride=1)
  → UART_VADDR.store           # 先于 register，避免 stray IRQ 早返回
  → register(10)               # RED: set_enable 仍 TODO，warning 保留
  → set_enable(10, true)
  → uart.init(Config::default())
  → main loop: 只报告 irq_count + rx_byte_count，不与 handler 竞争 RBR
```

- 启动无 StoreFault / panic / exception
- `register(10)=true`
- 两条 `set_enable is not implemented for IRQ 10` warning（RED 预期）
- `init ok (IER.DATA_READY enabled)`
- 6s 内 503~519 个 heartbeat 全部 `count=0 rx=0`
- SBI console 持续输出，无 unhandled IRQ
