## 1. 目标与结论

目标不是重新设计一套异步串口，而是把 StarryOS 已经在 RISC-V QEMU 上验证的闭环迁回当前 ArceOS 仓库，并把 StarryOS 专属的 TTY/VFS 部分留在边界之外。

StarryOS 已验证的核心链路是：

```text
PLIC IRQ 10
  -> axhal IRQ hook
  -> uart_16550 minimal ISR
  -> AtomicWaker
  -> axtask::future::block_on 驱动 RX/TX copier
  -> SPSC ring buffer
  -> PollSet
  -> TTY line discipline / read / write / poll
```

当前 ArceOS 0.2 与该基线存在两个结构性版本差异：

1. StarryOS 使用 `axtask/axhal 0.3.0-preview.2` 和 `axplat-riscv64-qemu-virt 0.3.1-pre.6`；当前 ArceOS 使用本仓库 0.2 模块和 `axplat-riscv64-qemu-virt 0.4.1`。
2. StarryOS 的依赖提供 Future `block_on`、IRQ hook、`axpoll::PollSet` 和完整 PLIC；当前 ArceOS 没有 Future executor，且 0.4.1 RISC-V platform 的 PLIC 是 TODO。

推荐策略是最小能力回移，不整体升级 ArceOS：从已验证版本移植 PLIC 和单 Future executor 的必要机制，当前 ArceOS 直接用 per-IRQ `axhal::irq::register(UART_IRQ, fn())`，无需照搬全局 IRQ hook。

## 2. StarryOS 可复用闭环

### 2.1 已验证的初始化顺序

StarryOS 在 scheduler 和内存管理已经可用的 `entry::init()` 中执行：

```text
iomap/确认 UART MMIO
  -> 读取 LSR/ISR 验证 stride=1
  -> 初始化 64 KiB RX/TX static ring
  -> 构造 Arc<AsyncUartDriver>
  -> 注册 ISR wrapper
  -> spawn RX copier
  -> spawn TX copier
  -> 创建 AsyncTty
  -> 绑定 init process stdio
```

这个顺序可复用，但 ArceOS 第一阶段不需要迁移 `AsyncTty`、line discipline、process stdio 和 `Pollable`。独立示例只需完成 ring 到 UART 的双向 echo。

### 2.2 可直接复用的 adapter

| StarryOS adapter | 原映射 | ArceOS 0.2 迁移方式 |
|------------------|--------|---------------------|
| `ArceOsRuntime::spawn` | `spawn_with_name(|| block_on(future))` | `spawn_raw(|| block_on(future), name, stack)` |
| `ArceOsRuntime::block_on` | `axtask::future::block_on` | 回移最小 `future::block_on` |
| `ArceOsMmio` | `axmm::iomap` + `phys_to_virt` | PoC 先使用已线性映射 UART MMIO；必要时启用 paging/iomap |
| `ArceOsSpinNoIrq` | `kspin::SpinNoIrq` | 可直接复用 |
| `ArceOsWakerSet` | `axpoll::PollSet` | PoC 可用 `axpoll`，或本地单消费者 waker set |
| `ArceOsUartPort` | `SpinNoIrq<Uart16550<MmioBackend>>` | 可直接复用，保持 stride=1 |
| ISR wrapper | 全局 `register_irq_hook(fn(usize))` | 使用 `register(UART_IRQ, fn())` 绑定单端口静态上下文 |

### 2.3 不应回移的 StarryOS 部分

- Linux TTY line discipline、job control、process session 和 PTY。
- `DeviceOps`、`Pollable`、`FIONBIO`、epoll 等 Linux 兼容层。
- 64 KiB ring buffer 作为固定配置；PoC 可先用 4 KiB，后续用压测选择。
- 全局 IRQ hook。当前 ArceOS 的 per-IRQ handler table 更适合单 UART PoC。
- StarryOS 的 LTO 性能参数。先建立正确性和调度基线，再做性能优化。

## 3. 当前 ArceOS 的最小补齐方案

### 3.1 PLIC

以 `axplat-riscv64-qemu-virt 0.3.1-pre.6` 的实现作为参考，将以下能力补到当前使用的 0.4.1 platform：

- `riscv_plic::Plic` 全局实例；
- supervisor context `hart_id * 2 + 1`；
- per-CPU context 初始化和 threshold；
- source priority、enable/disable；
- external interrupt claim；
- `HandlerTable::handle(claimed_irq)`；
- complete。

当前 ArceOS 仓库依赖 crates.io platform，实施前必须先选择可修改载体：推荐在同级 `axplat_crates` fork 上修复并临时使用 path/git patch，而不是把 PLIC 逻辑复制进 `axhal`。

### 3.2 单 Future executor

StarryOS 使用的 `axtask 0.3` `block_on` 很小，核心是 `AxWaker { WeakAxTaskRef, woke }`：

```text
poll Future
  -> Pending: 持有 woke lock 检查是否已被唤醒
  -> 未唤醒: blocked_resched
  -> Waker::wake: 设置 woke=true + unblock_task
  -> Ready: 返回
```

当前 `axtask 0.2` 已有 `current_run_queue`、`select_run_queue`、`blocked_resched` 和 `unblock_task`，且它们位于同一 crate 内，具备回移条件。应只回移 `block_on` 所需部分，不先引入 `poll_io`、timeout、interruptible 或完整 `axpoll` 集成。

必须增加两个测试：

- Future 先返回 Pending，外部任务 wake 后继续并 Ready；
- wake 发生在 poll 返回 Pending 与 blocked_resched 之间时，不丢唤醒。

### 3.3 PoC 承载位置

第一版建议创建 `examples/async_uart`，直接依赖 `axtask`、`axhal`、`kspin` 和本地 `uart_16550`：

- 应用 `main()` 执行时 scheduler、allocator 和平台 later-init 已完成；
- 无需先改 `axdriver` 设备模型；
- 无需替换 SBI console，所有调试日志仍可用；
- 成功后再把 adapter 提升到 `modules/axdriver` 或独立 `modules/axuart`。

PoC 明确限制为单 UART、单 reader、单 writer，符合当前 crate 的 SPSC 安全前提。

## 4. Milestone 路线

### M0：证据与边界（完成）

产出：当前 ArceOS 串口审计、`uart_16550` 审计、StarryOS 迁移映射。本阶段确认 StarryOS QEMU 基线有效，并识别版本差异。

### M1：设备中断基线

目标：不接入 async crate，仅证明 UART IRQ 10 可被正确 claim/complete。

验收：

- 注册最小 handler 后收到 UART RX IRQ；
- handler 能读取中断原因并计数；
- disable 后不再触发；重新 enable 后恢复；
- 连续输入无 IRQ storm；
- SBI console 日志保持可用。

### M2：Future 调度基线

目标：当前 `axtask` 可无轮询地驱动一个 Pending Future。

验收：

- `block_on` 单元测试覆盖正常 wake 和竞态 wake；
- Pending 任务进入 Blocked，而非 `yield_now` 循环；
- ISR/其他任务 wake 后进入 Ready；
- multitask + irq 和非 preempt 配置均能编译。

M1 与 M2 无代码依赖，可以并行推进。

### M3：Starry parity PoC

目标：在 `examples/async_uart` 复刻 StarryOS 的硬件到 ring 闭环。

验收：

- path 依赖启用 `uart_16550/async`；
- MMIO `0x1000_0000`、stride=1、UART IRQ 10；
- RX/TX copier 启动且空闲时处于 Blocked；
- 输入字节经 RX ring 读出并经 TX ring 回显；
- 不修改或替换 `axhal::console`。

### M4：QEMU 正确性与稳定性 Gate

目标：证明 PoC 不是偶然可用。

验收：

- 1B、64B、4 KiB 双向数据；
- 连续运行 10 分钟无 panic、丢唤醒和 IRQ storm；
- 统计 IRQ 次数、copier wake 次数、RX/TX drop；
- 空闲时 copier 不持续占用 CPU；
- QEMU 重复启动至少 20 次无初始化竞态。

### M5：接入 ArceOS stdio

目标：先替换输入数据源，再评估输出切换。

顺序：

1. `stdin` 从 RX ring 读取；
2. 空 ring 时用 waker/WaitQueue 阻塞，删除 yield-poll；
3. readiness 反映 ring 状态；
4. 普通 stdout 可选进入 TX ring；
5. SBI 始终保留给 early boot、panic 和 fallback log。

### M6：原生化与硬化

目标：从示例提升为可维护的 ArceOS 设备能力。

- 决定落入 `axdriver::uart` 还是独立 `axuart`；
- 修复/约束 `uart_16550` 的 SPSC 多生产者、per-port waker、IER 原子更新、真正 async read/flush 等问题；
- 增加多 UART/SMP 设计或明确不支持；
- 建立 StarryOS Q12/Q13 与 ArceOS 的回归指标；
- 最后沉淀通用中断 bottom-half 模式。

## 5. 依赖关系与关键路径

```text
M1 PLIC ───────────────┐
                       ├─> M3 parity PoC -> M4 QEMU Gate -> M5 stdio -> M6 hardening
M2 Future block_on ────┘

uart_16550 当前分支 ────────────────────────┘
```

关键路径是 M1 + M2 -> M3 -> M4。任何 TTY、poll、性能或通用设备模型工作都不应插入 M4 之前。

## 6. 风险与决策点

| 风险 | 处理 |
|------|------|
| platform crate 不在当前仓库 | 先建立可修改 fork/path patch，避免在 Cargo registry 上打补丁 |
| console 与 async UART 共用硬件 | PoC 不替换 console；调试输出走 SBI，UART 数据路径独立 |
| `uart_16550` 当前只适合单端口 SPSC | PoC 固定单 reader/writer；M6 再硬化 |
| IRQ 在 driver 初始化前到达 | 顺序固定为 ring/driver/waker -> handler -> IER/PLIC enable |
| Future 丢唤醒 | 复用 0.3 的 `woke` handshake，并做竞态测试 |
| QEMU 成功不代表真板 | M4 只作为 ArceOS QEMU gate；VisionFive2 保留为后续硬件 gate |

## 7. 推荐的第一个实现切片

第一个切片只包含：

1. 为 platform 0.4.1 恢复 PLIC；
2. 在 `axtask` 增加最小 `future::block_on`；
3. 新建 `examples/async_uart`，移植 StarryOS `os_arceos.rs` 和 `uart_init.rs` 的必要部分；
4. 实现输入一字节、异步回显一字节；
5. 记录 IRQ/wake 计数并验证任务空闲阻塞。

这已经能回答“异步串口是否真正应用到 ArceOS”，无需等待 TTY 或 POSIX 层完成。
