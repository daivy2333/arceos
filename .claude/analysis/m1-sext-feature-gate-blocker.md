# M1 S_EXT 不触发：feature gate 根因与执行方案

> Part of ArceOS codebase analysis (branch: `async-uart-1`)
> Generated by openspec-explorer at 2026-06-19
> See also: [M1 UART IRQ probe 阻塞分析](m1-uart-irq-probe-blocker.md), [StarryOS 到 ArceOS 迁移路线](starry-to-arceos-async-uart-roadmap.md)

---

## 1. 结论

M1-T3.1 当前阻塞的首要根因不是 OpenSBI 中断委托或 PLIC context，而是 `examples/uart_irq` 的 Cargo feature 接线不完整：probe 直接启用了 `axhal/irq`，却没有启用 `axstd/irq`（继而没有启用 `axfeat/irq` 和 `axruntime/irq`）。

因此，平台代码会设置 `sie.SEIE`、配置 PLIC context 1 和 source 10，但 `axruntime::init_interrupt()` 未被编译，最终负责设置全局 `sstatus.SIE` 的 `axhal::asm::enable_irqs()` 没有执行。PLIC 可以 pending，软件主动读取 claim register 也能得到 IRQ 10，但 CPU 不会进入 supervisor external interrupt trap。

最小修复应落在 probe 的 feature 声明，而不是在平台代码中重复设置全局 SIE：将 `examples/uart_irq/Cargo.toml` 的 `axstd` features 从 `["alloc"]` 改为 `["alloc", "irq"]`。这会沿项目既有顶层 feature 路径启用 `axruntime/irq`，并保留 runtime 统一注册 timer、最后开启全局中断的初始化顺序。

## 2. 完整因果链

### 2.1 当前硬件与平台链路已经成立

```text
UART RX
  -> IER.DATA_READY=1, FCR trigger=1, MCR.OUT2=1
  -> PLIC source 10, priority=1
  -> supervisor context 1 enable bit=1, threshold=0
  -> 手工 claim(context 1) 可返回 10
```

现有日志 `/tmp/m1-fcr.log` 给出 `claim_reg=0x0a`；这证明 UART 到 PLIC context 1 的设备侧链路已成立。读取 claim register 是有副作用的，会把 source 标记为 claimed，不能作为无侵入 pending probe，也不能与正常 trap handler 竞争。

### 2.2 delegation 已成立

OpenSBI 启动日志显示：

```text
Boot HART MIDELEG : 0x0000000000001666
Domain0 Next Mode : S-mode
```

`0x1666 & (1 << 9) != 0`，即 supervisor external interrupt（SEIP，bit 9）已经委托到 S-mode。继续修改 `mideleg/medeleg` 不是当前首选路径；S-mode 也不应自行写 M-mode delegation CSR。

### 2.3 CPU 侧只完成了局部 enable

`vendor/axplat-riscv64-qemu-virt/src/init.rs` 在 later-init 中调用：

```text
irq::init_percpu()  -> sie::set_sext()
plic::init_percpu() -> context 1 threshold=0
```

这只设置 `sie.SEIE`。RISC-V 接收 S-mode interrupt 还要求全局 `sstatus.SIE=1`。

全局 enable 位于 `modules/axruntime/src/lib.rs::init_interrupt()` 末尾：

```rust
#[cfg(feature = "irq")]
fn init_interrupt() {
    // register timer handler ...
    axhal::asm::enable_irqs();
}
```

而该函数及其调用都受 `axruntime` 自身的 `irq` feature 控制。

### 2.4 probe 的 feature graph 缺口

当前 `examples/uart_irq/Cargo.toml`：

```toml
axstd = { workspace = true, features = ["alloc"] }
axhal = { workspace = true, features = ["irq", "defplat"] }
```

Cargo feature 只会对同一个 package 合并。启用 `axhal/irq` 不等于启用 `axruntime/irq`。当前 `cargo tree -e features -i axruntime` 只显示 `axruntime/alloc` 和 default；运行日志也缺少 `Initialize interrupt handlers...`，与 `init_interrupt()` 未编译完全一致。

项目定义的正确传播链是：

```text
axstd/irq
  -> axfeat/irq
    -> axhal/irq
    -> axruntime/irq
    -> axtask?/irq
```

使用 `cargo tree ... --features axstd/irq` 已确认 `axruntime feature "irq"` 被激活。

## 3. 执行计划

### Phase A：最小 feature 修复

仅修改 `examples/uart_irq/Cargo.toml`：

```diff
-axstd = { workspace = true, features = ["alloc"] }
+axstd = { workspace = true, features = ["alloc", "irq"] }
```

保留 `axhal = ... features = ["irq", "defplat"]`，因为 probe 直接调用 `axhal::irq` 和 `axhal::mem`；Cargo 会合并重复的 `axhal/irq`，不会产生第二套状态。

不建议在 `run_riscv()` 中直接调用 `axhal::asm::enable_irqs()`。这样会绕过 runtime 的 timer handler 初始化，掩盖应用 feature 配置错误，并使测试夹具与真实 ArceOS 启动路径不同。

### Phase B：静态 Gate

执行：

```bash
cargo tree -p arceos-uart-irq -e features -i axruntime \
  --target riscv64gc-unknown-none-elf
make A=examples/uart_irq ARCH=riscv64 SMP=1 build
make A=examples/uart_irq ARCH=riscv64 SMP=4 build
```

验收：

- feature tree 包含 `axruntime feature "irq"`；
- SMP=1/4 均编译通过；
- 启动日志出现 `Initialize interrupt handlers...`。

### Phase C：CSR 与 trap Gate

在临时诊断中、开启 UART IRQ 前读取并打印一次 CSR：

```text
sstatus.SIE = 1
sie.SEIE    = 1
mideleg[9]  = 1          # 由 OpenSBI 日志确认，不在 S-mode 读取 M CSR
```

注入 1 byte 后验收：

```text
S_EXT trap entered
claim(ctx=1) = 10
IRQ10_COUNT += 1
RX_BYTE_COUNT += 1
complete(ctx=1, 10)
```

不要在主循环读取 claim register；该读取会消费 claim。若需要无侵入观察，读取 pending bitmap、enable、priority、threshold 和 S-mode CSR。

### Phase D：M1 后续 Gate

T3.1 通过后，按既有 OpenSpec 顺序执行：

1. T3.2 disable/re-enable：disable 区间计数不变，re-enable 后恢复。
2. T3.3 duplicate/unregister/unhandled/spurious：均 complete、无 storm。
3. T4.1-T4.4：RISC-V 启动、1B/64B、无输入和非 RISC-V build matrix。
4. T4.5：spec compliance、quality review 与 vendor patch 回滚演练。

## 4. 失败分叉

如果启用 `axstd/irq` 后仍无 `S_EXT`，按以下顺序继续，禁止跳回宽泛猜测：

| 检查 | 判定 | 后续动作 |
|------|------|----------|
| 启动日志无 `Initialize interrupt handlers...` | feature 仍未传播到最终构建 | 保存完整 cargo 命令并检查 Makefile feature 参数覆盖 |
| `sstatus.SIE=0` | runtime enable 未执行或被错误恢复 | 追踪 `enable_irqs()` 后的 irq-save guard 生命周期 |
| `sstatus.SIE=1`、`sie.SEIE=0` | platform per-hart init 缺失 | 检查 `init_later(cpu_id)` 调用与 cfg(feature="irq") |
| CSR 正确、pending=0 | UART/输入侧问题 | 回到 IER/MCR/FCR/IIR/LSR 检查，不读 claim |
| CSR 正确、pending=1、无 trap | PLIC target/QEMU wiring 问题 | 用 QEMU irq trace/GDB 检查 SEIP，不修改 delegation CSR |
| 进入 S_EXT、claim=0 | source 已被诊断读取消费或 context 不一致 | 删除 claim polling，核对 context-local register 地址 |

## 5. 风险与边界

- 该结论基于当前单核运行证据。`CURRENT_CONTEXT: AtomicUsize` 在 SMP 下不是 per-CPU，后续 AP 真正接收设备 IRQ 前必须改为 per-CPU context 或从当前 CPU ID 计算；这不阻塞 SMP=1 的 T3.1。
- `SpinNoIrq` 的 claim/complete 锁边界正确地避开了 handler，但应继续保持 claim 后释放锁、handler 返回后再 complete。
- 手工 claim 日志是有副作用的历史诊断证据；后续验收必须由 trap 内 claim 产生。
